# SD_04 아키텍처 설계서 생성 프롬프트

유스케이스는 **무엇을**, 프로세스는 **어떤 순서로**, 화면은 **어떻게 조작하는지**, 데이터베이스는 **어디에 담는지**를 답했다.
아직 답하지 않은 질문이 하나 남는다 — **누가 이 기능을 담당하는가.** 이 문서가 그것을 정한다.

## 프롬프트

### [역할]

너는 업무 시스템의 모듈 구조와 계층 아키텍처를 설계하는 **선임 아키텍트**다.
전문영역은 (1) 모듈 경계 판정 (2) 기능 아키타입 분류 (3) ArchiMate 3.2 계층 모델링
(4) 의존 그래프 분석 (5) 제공 인터페이스 도출이다.

### [맥락]

독자는 구현을 배분할 **개발 리드**와 API 를 설계할 **인터페이스 설계자**다.
**여기서 나온 모듈의 제공 인터페이스가 그대로 API 카탈로그의 입력**이 된다.
모듈 경계가 틀리면 API 가 서로의 데이터를 넘나들며 호출하게 되고, 그때는 되돌리기 어렵다.

### [근거 규율] — 최우선

1. **모듈 경계는 취향이 아니라 규칙으로 정한다.** 아래 세 기준 외의 근거로 모듈을 가르지 않는다.
2. **모든 테이블이 어느 모듈에 배정되었는지** 답해져야 한다. 배정되지 않은 테이블은 소유자 없는 데이터다.
3. **쓰기 소유가 겹치면 안 된다.** 두 모듈이 같은 테이블에 쓰면 그 둘은 사실 하나의 모듈이거나, 테이블이 잘못 설계된 것이다.
   불가피한 예외는 **그 사실과 충돌하지 않는 이유**(행이 종류로 갈린다 등)를 미해결 절에 적는다.
4. 상류 문서에 없는 모듈·외부시스템·기술요소를 만들지 않는다.

### [작성 절차]

1. **모듈 경계 판정** — 세 기준을 순서대로 적용한다.

   | 기준 | 내용 | 적용 |
   |---|---|---|
   | **1. 데이터 소유** | 한 테이블 묶음의 **쓰기 권한은 한 모듈만** 가진다 | SD_03 의 엔티티 전수를 모듈에 배타 배정 |
   | **2. 유스케이스 정합** | 한 유스케이스는 **한 모듈이 주도**한다 (보조 모듈은 허용) | UC 마다 주도 모듈 1개 |
   | **3. 게이트 경계** | **게이트를 사이에 둔 두 행위는 다른 모듈**이다 | SD_01 게이트가 모듈을 가른다 |

   기준 1이 가장 강하다. 셋이 충돌하면 1을 따른다.
2. **아키타입 분류** — 모듈의 «성격»을 분류한다. 여러 대상(팀·도메인)에 같은 분류를 적용해야 인터페이스 모양이 일관된다.
   아래 9종을 기본으로 쓰고, 도메인에 맞게 가감하되 **가감한 이유를 적는다.**

   | 코드 | 아키타입 | 하는 일 | 전형적 인터페이스 |
   |---|---|---|---|
   | **IN** | 수집 | 외부 입력을 시스템 안으로 들인다 | `POST /{res}` · `POST /{res}/import` |
   | **VA** | 검증 | 누락·형식·규칙을 판정한다 | `POST /{res}/validate` · `GET /{res}/findings` |
   | **RF** | 참조 | 기준 데이터를 조회·판본 고정한다 | `GET /{res}` · `POST /{res}/pin` |
   | **GE** | 생성 | 산출물 초안을 만든다 | `POST /{res}/compose` · `GET /{res}/{id}` |
   | **RV** | 검토 | 두 대상을 비교하고 차이를 남긴다 | `POST /{res}/compare` |
   | **AP** | 승인 | 단계 승인과 게이트를 판정·해제한다 | `POST /{res}/approve` · `POST /gates/{code}/clear` |
   | **EX** | 반출 | 외부로 내보내고 감사 기록을 남긴다 | `POST /{res}/export` · `POST /{res}/dispatch` |
   | **EV** | 근거 | 근거를 부착하고 역추적을 제공한다 | `POST /evidence` · `GET /trace/{type}/{id}` |
   | **RU** | 실행 | 작업을 돌리고 재현 가능하게 기록한다 | `POST /runs` · `GET /runs/{id}` |

   분포표를 만들고 **편중이 있으면 그 의미를 해석한다.** 편중은 대개 결함이 아니라 도메인의 성질이다
   (생성이 몰리면 그 시스템은 본질적으로 산출물 생성 시스템이다).
3. **모듈 목록** — 표 열: `ID | 모듈 | 아키타입 | 주도 UC | 프로세스 | 쓰기 소유 테이블`.
   읽기 전용 기준 데이터는 관리 모듈을 지정하고 «누가 읽는지»를 본문에 적는다.
4. **계층 도면 4장** — 한 도면에 모두 담으면 읽을 수 없으므로 관점별로 나눈다.
   ① **전체 아키텍처** — 비즈니스·애플리케이션·기술 3계층 조감
   ② **프로세스 대 모듈 배치** — 프로세스 단계를 어느 모듈이 담당하고 게이트가 어디서 막는지
   ③ **모듈 간 의존** — 호출·공급 관계
   ④ **공통모듈 연계** — 팀 모듈이 공통 기능 중 무엇을 참조하는지 (공통모듈이 있을 때)
   도면마다 아래에 **«읽는 법»** 한 문단을 붙인다. 도면은 스스로를 설명하지 않는다.
5. **의존 규칙 점검** — 표로 닫는다: `순환 의존 | 말단 모듈 | 최다 피의존 모듈 | 데이터 소유 중복`.
   **순환이 있으면 설계를 고친다.** 특히 **모든 모듈이 필요로 하는 모듈(근거·감사 등)은 아무도 호출하지 않는 말단**이어야 한다 —
   그 모듈이 남을 부르는 순간 곧바로 순환이 생긴다.
6. **제공 인터페이스** — 모듈이 밖에 내놓는 것과 주 소비자를 표로. **아키타입이 같으면 인터페이스 모양도 같다.**
   세부 엔드포인트·게이트웨이 배치는 이 문서에서 하지 않고 API 문서로 넘긴다.
7. **미해결** — 기준 1의 예외, 아키타입 미배정, 소유 애매한 기준 데이터를 숨기지 않고 적는다.

**검증된 요소 매크로** — 계층별로 쓸 것만 쓴다.

| 계층 | 매크로 | 의미 |
|---|---|---|
| Business | `Business_Actor` · `Business_Process` · `Business_Service` · `Business_Object` · `Business_Event` | 사람이 하는 일과 그 산출물 |
| Application | `Application_Component` · `Application_Service` · `Application_Function` · `Application_Interface` · `Application_DataObject` | 시스템이 하는 일 |
| Technology | `Technology_Node` · `Technology_Service` · `Technology_Artifact` | 그것이 도는 곳 |

| 관계 | 매크로 | 의미 |
|---|---|---|

**작성 규약**

- **§1-2 에 위 두 표를 싣는다.** 표기를 밝히지 않은 ArchiMate 도면은 독자마다 다르게 읽힌다.
- 계층은 `package "비즈니스 계층"` 처럼 **명시적으로 묶는다.** 모듈이 많으면 계층 안에서 성격별로 한 번 더 묶는다.
- 요소 라벨에 **모듈 ID 와 아키타입 코드를 함께** 넣는다: `"M06 견적서 생성 (GE)"`.
- `_Up` 접미 매크로는 화살표를 위로 세운다 — **계층 방향(기술 → 애플리케이션 → 비즈니스)을 지키면 도면이 저절로 정렬된다.**
- 한 도면의 요소는 **25개 이하**로 유지한다. 넘으면 관점을 더 쪼갠다(§4~§7 이 이미 그 분할이다).

### [렌더 — plantuml.sumzip.com]

```python
import base64, zlib
enc = base64.urlsafe_b64encode(zlib.compress(소스.encode("utf-8"), 9)).decode("ascii")
url = "https://plantuml.sumzip.com/plantuml/svg/" + enc      # 경로는 반드시 /plantuml/svg/
```

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' --max-time 20 "<렌더URL>"   # 200 image/svg+xml
```

- **모든 도면에 렌더 링크를 단다.** 기존 SD_04 문서들은 PlantUML 소스만 있고 링크가 없어 아무도 그림을 보지 못했다.
  이 프롬프트의 산출물에서는 그 상태를 허용하지 않는다.
- **HTTP 400 = 문법 오류.** 존재하지 않는 매크로명을 쓰면 여기서 걸린다 — 위 표에 있는 이름만 쓴다.
- 200 이어도 SVG 안에 `Syntax Error` 가 있으면 실패다. URL 4096자 이하(넘으면 관점을 쪼갠다).
- 소스를 고치면 재인코딩하고, 복호해서 코드블록과 대조한다.
- 삽입 형식: `**[「<도면명>」 PlantUML 뷰어로 열기](<url>)** — 클릭 시 브라우저로 연결됩니다.`
