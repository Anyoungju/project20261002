# SD_02 UI/UX 설계서 생성 프롬프트

프로세스는 "무엇을 어떤 순서로"까지만 답한다. 사람이 그 일을 **실제로 하려면 화면이 필요하다.**
이 문서는 프로세스를 조작 가능한 화면으로 옮기고, **막힌 지점을 사람이 알아볼 수 있게** 만든다.

## 입력

| 항목 | 값 |
|---|---|
| 프로세스 설계서 | `{출력폴더}/SD_01_프로세스설계서_{대상명}.md` — IPO · **게이트 맵** · 인계 계약 |
| 유스케이스 | `{출력폴더}/UC_00_개요_*.md` + `UC_*.md` 전건 — 액터 · 기본흐름 · 대체흐름 · 업무규칙 |
| 원천 | `{원천}` — 성공기준·실패모드 블록 (원칙 역산의 근거) |
| 출력 경로 | `{출력폴더}/SD_02_UIUX설계서_{대상명}.md` |

**SD_01 이 없으면 시작하지 않는다.** 게이트 맵 없이 그린 화면은 "막히는 자리"를 모르기 때문에 반드시 다시 그려야 한다.

---

## 프롬프트

### [역할]

너는 업무 시스템의 화면을 설계하는 **선임 UI/UX 설계자**다.
전문영역은 (1) 프로세스-화면 사상 (2) 내비게이션 구조 설계 (3) 게이트의 화면 표현
(4) 공통 컴포넌트 추출 (5) 역할별 뷰 분리다.

### [맥락]

독자는 이 문서로 화면을 구현할 **프론트엔드 개발자**와, 여기서 나온 표시 항목으로 테이블을 설계할 **데이터 설계자**다.
**화면이 요구하는 데이터가 곧 다음 문서(SD_03)의 컬럼이 된다.** 그래서 UI를 DB보다 먼저 설계한다 —
화면 없이 ERD를 그리면 "있으면 좋을 것 같은" 컬럼이 들어가고, 화면부터 그리면 안 쓰이는 컬럼이 드러난다.

### [근거 규율] — 최우선

1. **설계 원칙을 상상으로 만들지 않는다.** SD_01 §게이트 맵과 업무규칙에서 **역산**한다.
   원칙마다 `근거`(BR·게이트·원천 블록)와 `컴포넌트로의 귀결`을 함께 적는다.
2. **모든 컴포넌트는 어느 UC의 어느 단계에 대응하는지 답할 수 있어야 한다.** 대응이 없는 컴포넌트는 **지운다.**
3. **화면에 뜨는 값에는 출처가 있다.** 각 표시 항목이 어느 IPO 단계의 Output 인지 `데이터 바인딩` 열에 적는다.
4. 원천·상류 문서에 없는 기능(알림·채팅·대시보드 등)을 **취향으로 추가하지 않는다.**

### [작성 절차]

1. **설계 원칙 역산** — 게이트 맵과 BR을 훑어 원칙 `U1`~`UN`(5~8개)을 세운다.
   표 열: `# | 원칙 | 근거 | 컴포넌트로의 귀결`.
   이어서 **«원칙이 배제한 흔한 선택»** 표를 붙인다(흔한 선택 · 배제 이유). 무엇을 하지 않기로 했는지가 설계다.
2. **화면 목록** — 프로세스 `PN` 하나에 화면 `SN` 하나를 기본으로 사상한다.
   표 열: `화면 | 명칭 | 대응 프로세스 | 주 사용자 | 성격`.
   한 프로세스가 두 역할의 서로 다른 판단을 요구하면 **역할별 뷰로 나눈다**(같은 화면 두 벌).
3. **내비게이션 트리** — 화면 간 이동 경로를 도면으로. 이동 화살표에 **통과 조건(게이트 ID)** 을 라벨로 단다.
   되돌아가는 경로(반려·재검토)는 점선으로 구분한다.
4. **진행 레일** — 전 화면 상단에 고정되는 단계 표시를 정의한다. 사용자가 "지금 어디이고 어디가 막혔는지"를 상시 본다.
5. **공통 컴포넌트 추출** — 두 화면 이상에 나타나는 것을 `C1`~`CN`으로 뽑는다.
   표 열: `ID | 컴포넌트 | 용도 | 근거 원칙`. 컴포넌트마다 **상태·변형·동작**을 별도 소절로 기술한다.
6. **화면별 설계** — 화면마다 아래 네 가지를 **모두** 쓴다.
   - `N-1 와이어프레임` — salt 도면
   - `N-2 영역별 설계` — 표 열: `영역 | 내용 | 데이터 바인딩 | UX 의도`. UX 의도에는 근거 원칙 ID를 박는다
   - `N-3 상호작용` — 표 열: `조작 | 동작 | 근거`
   - `N-4 상태 전이` — 화면이 가질 수 있는 상태와 전이 조건
7. **게이트 → 화면 사상** — SD_01 게이트 **전건**에 대해 표를 만든다.
   열: `게이트 | 화면 | UI 표현 | 비활성화 대상 | 해제 액션`. **이 표가 두 문서의 정합성 검사 지점이다.**
   이어 사상 규칙을 적는다 — 최소한 다음 네 가지를 포함한다:
   ① 모든 게이트는 **하나 이상의 버튼을 비활성화**한다(배너만 띄우고 진행 가능하면 게이트가 아니다)
   ② 비활성 버튼에는 **이유가 붙는다**(hover 시 동일 문구)
   ③ **해제 주체가 현재 사용자가 아니면 액션은 «요청 보내기»** 다(직접 해제 버튼은 권한 우회를 부른다)
   ④ 두 화면에 걸치는 게이트는 **문구를 동일하게** 유지한다
8. **상태 표현·접근성·오류 규약** — 상태 아이콘 사용 규약, 키보드·명암·스크린리더, 장애 시 표현(전역 실패 규칙).

### [문서 구조] — 이 순서를 지킨다

```
§1 설계 원칙                     (+ 1-1 원칙이 배제한 흔한 선택)
§2 화면 지도와 내비게이션          2-1 화면 목록 · 2-2 내비게이션 구조(도면) · 2-3 진행 레일
§3 공통 컴포넌트                 3-1 컴포넌트 목록 · 3-2~ 컴포넌트별 상세(도면 포함)
§4 ~ §N 화면별 (S1, S2, … 각각 한 절)
        N-1 와이어프레임 · N-2 영역별 설계 · N-3 상호작용 · N-4 상태 전이 (역할별 뷰가 있으면 와이어프레임 2벌)
§N+1 게이트 맵 → 화면 표현 사상    (+ 사상 규칙)
§N+2 상태 표현·접근성·오류 규약
§N+3 미해결·확인 필요
```

도면 수는 **14개 내외**가 기준이다(내비게이션 1 + 컴포넌트 2~3 + 화면별 와이어프레임 7~9 + 상태·흐름 1~2).

### [다이어그램 1 — 내비게이션 트리]

```
@startuml
skinparam backgroundColor #F3F1EB
skinparam shadowing false
title 화면 지도와 이동 경로

rectangle "작업 목록\n(진입 홈)" as HOME
rectangle "S1 요청 접수·검증" as S1
rectangle "출처 드로어\n(전 화면 오버레이)" as DRAWER

HOME --> S1
S1 --> S2 : G1·G2 통과
S5 ..> S2 : 재검토 요구 A2
S1 ..> DRAWER

note bottom of DRAWER
  근거 칩 클릭 시 열린다.
  화면 전환 없이 원천을 확인한다.
end note
@enduml
```

- 노드는 `rectangle`, 줄바꿈은 `\n`.
- **전진은 실선 + 게이트 라벨**, **반려·오버레이는 점선**. 이 구분이 없으면 트리가 아니라 그래프가 된다.

### [다이어그램 2 — 화면 인터페이스 (salt)]

`@startuml` 다음 줄에 **`salt`** 를 둔다. 검증된 위젯:

| 용도 | 구문 |
|---|---|
| 전체 묶음 | `{ … }` · 테두리 있는 묶음 `{+ … }` |
| 행 구분선 | `..` |
| 열 분할 | `\|` (같은 행 안에서) |
| 제목 있는 그룹 | `{^"추출 결과  요구사항 6항목" … }` |
| 표 | `{# 헤더1 \| 헤더2` 다음 줄부터 데이터 행 `}` |
| 탭 | `{/ <b>원가 \| 근거 \| 교차검증 }` |
| 스크롤 텍스트 | `{S 여러 줄 본문 }` |
| 버튼 | `[라벨]` · 비활성 표기는 `[라벨 (비활성)]` |
| 입력칸 | `"플레이스홀더  "` |
| 드롭다운 | `^항목1^` |
| 체크박스 · 라디오 | `[ ]` `[X]` · `( )` `(X)` |
| 강조 | `<b>텍스트` |

**작성 규약**

- 와이어프레임 **맨 위 행에 진행 레일**을 둔다: `{ <b>건 번호  \|  진행: [1 검증] > 2 설계 > 3 원가 }`.
- **게이트 차단 상태를 그린다.** 정상 상태만 그린 와이어프레임은 이 설계서의 핵심을 빠뜨린 것이다.
  차단 블록에는 `사유 · 해제 주체 · 다음 행동 버튼` 셋을 함께 넣는다.
- 비활성 버튼을 **명시적으로** 표기한다(`[다음 단계로 (비활성)]`).
- 실데이터처럼 보이는 예시 값을 넣되 **개인정보는 마스킹 형태**로 쓴다(`***@***.kr`).
- 도면 하나가 한 화면이다. 화면 두 개를 한 도면에 넣지 않는다.

### [렌더 — plantuml.sumzip.com]

```python
import base64, zlib
enc = base64.urlsafe_b64encode(zlib.compress(소스.encode("utf-8"), 9)).decode("ascii")
url = "https://plantuml.sumzip.com/plantuml/svg/" + enc      # 경로는 반드시 /plantuml/svg/
```

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' --max-time 20 "<렌더URL>"   # 200 image/svg+xml
```

- **HTTP 400 이면 문법 오류다.** salt 는 중괄호 짝이 맞지 않으면 통째로 실패하므로 **여는 `{` 와 닫는 `}` 수를 먼저 센다.**
- 200 이어도 SVG 안에 `Syntax Error` 가 있으면 실패다. URL은 **4096자 이하**(넘으면 화면을 영역별로 쪼갠다).
- 소스를 고치면 재인코딩하고, 복호해서 코드블록과 대조한다.
- 삽입 형식: `**[「<화면명>」 PlantUML 뷰어로 열기](<url>)** — 클릭 시 브라우저로 연결됩니다.`

### [검증 — 저장 직전 자가점검]

- [ ] 모든 원칙에 **근거**(BR·게이트·원천 블록)가 붙었는가 — 상상으로 만든 원칙 0건
- [ ] 모든 프로세스가 화면으로 **사상**되었는가 (누락 프로세스 0건)
- [ ] 모든 컴포넌트가 **어느 UC의 어느 단계**에 대응하는지 답해지는가
- [ ] 모든 표시 항목에 **데이터 바인딩**(IPO Output)이 적혔는가
- [ ] SD_01 게이트 **전건**이 사상표에 있는가 · 각 게이트가 **버튼을 비활성화**하는가
- [ ] 해제 주체가 타인인 게이트의 액션이 «요청»인가 (직접 해제 버튼 0건)
- [ ] 와이어프레임에 **차단 상태**가 그려졌는가 (정상 상태만 있는 화면 0건)
- [ ] 두 역할이 다른 판단을 하는 화면이 **역할별 뷰**로 나뉘었는가
- [ ] 개인정보 예시가 마스킹되었는가
- [ ] 모든 렌더 링크가 **curl 200 · image/svg+xml** 이고 `Syntax Error` 가 없는가
- [ ] 링크를 복호한 소스가 **코드블록과 글자까지 같은가** · URL 4096자 이하인가
- [ ] 이모지·긴 URL 노출이 없는가

### [금지]

- 상류 문서에 없는 기능·화면 추가
- 게이트를 토스트·경고로 표현 (사라지는 것은 벽이 아니다)
- 결측 항목을 회색 placeholder 로 처리 ("아직 안 채움"과 "채우면 안 됨"이 구분되지 않는다)
- 이모지 · 긴 URL 원문 노출
