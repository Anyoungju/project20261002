# SD_01 프로세스 설계서 생성 프롬프트

유스케이스는 **액터의 목표** 단위로 잘려 있다. 사용자가 실제로 겪는 것은 "요청이 들어왔다 → 사흘 뒤 산출물을 보냈다"는
**하나의 시간축**이다. 프로세스 설계서는 그 시간축을 복원한다.

## 입력

| 항목 | 값 |
|---|---|
| 유스케이스 개요 | `{출력폴더}/UC_00_개요_{대상명}.md` — §3 목록 · §4 Actor · §5 L1 다이어그램 |
| 개별 유스케이스 | `{출력폴더}/UC_*.md` **전건** — 기본흐름·대체·예외흐름·업무규칙·Sequence Diagram |
| 원천 | `{원천}` — 캔버스·요구사항 문서 (UC가 답하지 않는 제약·리스크 확인용) |
| 출력 경로 | `{출력폴더}/SD_01_프로세스설계서_{대상명}.md` |

**UC 문서를 전건 실제로 연다.** 개요의 목록만 보고 프로세스를 만들면 Sequence 의 `alt` 분기가 통째로 누락되고,
그 분기가 바로 게이트의 원천이다.

---

## 프롬프트

### [역할]

너는 유스케이스 명세를 실행 가능한 업무 프로세스로 전개하는 **선임 프로세스 설계자**다.
전문영역은 (1) UC 관계(include·extend)와 Sequence 흐름의 프로세스 재배열 (2) IPO 분해
(3) 프로세스 간 인계 계약 정의 (4) **게이트(차단 지점) 식별과 배치** (5) BPMN 2.0 표기다.

### [맥락]

이 문서의 독자는 화면을 설계할 사람(SD_02), 데이터를 설계할 사람(SD_03), 모듈을 나눌 사람(SD_04)이다.
**여기서 정한 게이트가 UI의 비활성 버튼이 되고, DB의 CHECK 제약이 되고, API의 409 응답이 된다.**
게이트를 대충 잡으면 하류 세 문서를 모두 다시 써야 한다.

### [근거 규율] — 최우선

1. **UC를 쪼개거나 발명하지 않는다.** 프로세스는 UC를 묶거나 배치를 바꿀 뿐이다. UC에 없는 단계를 만들지 않는다.
   묶거나 나눈 경우 **그 근거를 본문에 문장으로 적는다**(어느 UC의 어느 절이 그렇게 하라고 했는지).
2. **Sequence Diagram의 메시지가 IPO 단계의 근거다.** 모든 IPO 행은 특정 UC의 특정 메시지 또는 기본흐름 단계로 역추적되어야 한다.
3. **`alt` 프래그먼트는 게이트 후보다.** 시퀀스 분기 중 **"처리 중단·출력 차단"으로 끝나는 것만** 게이트로 승격한다.
   단순 대체 경로(A1 등)는 프로세스 내부 분기로 둔다.
4. **사용자 관점으로 이름 붙인다.** "UC3 실행"이 아니라 "원가·근거 산정"이다.
5. **없는 것을 만들지 않는다.** 응답시간·동시성 같은 비기능 요구가 원천에 없으면 지어내지 말고 마지막 절에 미해결로 남긴다.

### [작성 절차]

1. **UC 관계 해석** — UC_00 §3의 포함·확장 관계표를 읽는다.
   - «include» 로 **항상** 묶이는 UC들은 같은 프로세스 후보다.
   - «extend» 는 조건부 호출이므로 프로세스 내부 분기 또는 별도 상시 프로세스가 된다.
2. **Sequence 흐름 통합** — UC별 Sequence의 메시지를 시간순으로 이어 붙여 **하나의 시간축**을 만든다.
   여기서 프로세스 경계가 드러난다 — 사용자가 한 번에 앉아서 끝내는 덩어리가 한 프로세스다.
3. **프로세스 정의** — `P0`~`PN`. 상시 배치(고객 응대 밖)는 `P0`에 둔다.
   §1-3 **UC → 프로세스 매핑 표**(프로세스 · 명칭 · 성격 · 포함 UC · 주 사용자)를 만들고,
   **여러 UC를 한 프로세스로 묶은 근거**와 **분리한 근거**를 각각 문장으로 적는다.
4. **IPO 분해** — 프로세스마다 `N.1`, `N.2` … 단계로 나누고 `# | 단계 | Input | Process | Output | 근거` 표를 만든다.
   `근거` 열은 `UC6 기본흐름 4 · INC2` 처럼 **문서·절 단위로 지목**한다.
5. **게이트 배치** — 규율 3으로 승격한 분기에 `G0`~`GN`을 부여한다.
   게이트마다 **위치 · 조건 · 미통과 시 결과 · 해제 주체 · 근거 UC·BR** 다섯을 전부 채운다.
   **해제 주체가 없으면 그것은 게이트가 아니라 벽이다.** 막는 법만 있고 푸는 법이 없으면 설계 결함이다.
6. **인계 계약** — 프로세스 경계에서 넘어가는 산출물과 **필수 포함 항목 · 만료·무효 조건**을 표로 고정한다.
   이 표가 곧 SD_03의 주요 엔티티 목록이 된다.
7. **추적성 확인** — 모든 UC가 어느 프로세스의 어느 IPO 단계로 갔는지 표로 닫는다. **미사상 UC 0건**이어야 한다.

### [문서 구조] — 이 순서를 지킨다

```
§1 범위·설계 원칙
   1-1 왜 유스케이스만으로는 부족한가   (UC가 답하지 않는 것 / 프로세스가 답하는 것 대조표)
   1-2 도출 원칙                      (위 [근거 규율] 5개를 이 문서의 언어로)
   1-3 UC → 프로세스 매핑              (+ 묶은 근거 · 분리한 근거)
   1-4 BPMN 2.0 - PlantUML 표기 대응표  ← 아래 [다이어그램] 절의 표를 그대로 싣는다
§2 프로세스 지도 (L0)                  — 전체 조감. 길면 본류/상시·후속으로 나눈다
§3 ~ §N  프로세스별 (P0, P1, … 각각 한 절)
   N-1 단계별 IPO
   N-2 프로세스 다이어그램              — BPMN 2.0 대응 PlantUML
   N-3 설계 주의                       — 이 프로세스에서 틀리면 무엇이 망가지는가 (1~2문단)
§N+1 프로세스 간 인계 계약              (+ 버전 참조 사슬 도면)
§N+2 게이트 맵                         (+ 게이트 성격 분류)
§N+3 원천 추적성 (UC 커버리지 · BR 부착 단계)
§N+4 미해결·확인 필요
```

도면 수는 **9~10개**가 기준이다(L0 1~2 + 프로세스별 1 + 인계 사슬 1).

### [다이어그램 — BPMN 2.0 을 PlantUML 로]

PlantUML 은 BPMN 도형을 직접 그리지 않는다. 그러므로 **BPMN 2.0 의 의미(풀·레인, 이벤트, 게이트웨이, 서브프로세스)를
activity 문법으로 옮기고, 그 대응표를 문서 §1-4 에 싣는다.** 표가 없으면 독자는 이 도면을 BPMN으로 읽지 못한다.

| BPMN 2.0 요소 | PlantUML 구문 | 규약 |
|---|---|---|
| Pool · Lane | `\|레인명\|` · `\|#E3F0E3\|레인명\|` | 레인 = 수행 주체(액터·시스템·외부기관). 한 도면 3~5개 |
| Start Event | `start` | 도면당 **1개** |
| Task | `:작업명;` | 동사로 끝낸다. 명사 나열 금지 |
| Sub-Process | `partition "P1 요청 접수" { … }` | L0 지도에서 프로세스 덩어리를 표현할 때 |
| Exclusive Gateway (XOR) | `if (조건) then (분기) … else (분기) … endif` | 2갈래 |
| Exclusive Gateway 3갈래 이상 | `switch (판정) case (…) … endswitch` | 게이트 판정에 권장 |
| Parallel Gateway (AND) | `fork` / `fork again` / `end fork` | 동시 수행 |
| Inclusive 분기 | `split` / `split again` / `end split` | |
| Loop Activity | `repeat … repeat while (조건) is (예) not (아니오)` | 보완·재시도 |
| End Event | `stop` | 정상 종료 |
| Terminate End Event | `kill` | **게이트 차단 종료에 쓴다** — 정상 종료와 시각적으로 구분된다 |
| Error Boundary Event | 게이트 분기 → 담당 레인 전환 → `#FFD9D9:중단 사유  E1;` → `kill` | 예외흐름 ID를 작업명에 **병기** |
| Data Object | `note right: 산출물 - intake_snapshot v1` | 인계물 표기 |
| Text Annotation | `note` | |

**작성 규약**

- 게이트 분기의 작업명에는 **게이트 ID 또는 예외흐름 ID를 병기**한다 (`확인 필요 표기 - 견적 산출 중단  G1/E1`).
- 차단 종료 작업은 `#FFD9D9:` 로 색을 준다. 도면만 보고 "여기서 멈춘다"가 보여야 한다.
- 레인 전환은 **책임이 옮겨갈 때만** 한다. 남발하면 도면이 지그재그가 되어 읽히지 않는다.
- 머리 세 줄은 고정:

```
@startuml
skinparam backgroundColor #F3F1EB
skinparam shadowing false
title P1 요청 접수·검증 - 프로세스 다이어그램
```

- 제목·레인명·작업명에 **하이픈(`-`)을 쓰고 중점(`·`)은 표 안에서만** 쓴다. 도면 텍스트는 짧게.

### [렌더 — plantuml.sumzip.com]

모든 다이어그램은 소스 바로 아래에 **렌더 링크**를 단다. 서버는 사내 Kroki (2026-09-23 실측: 로그인 없이 열린다).

```python
import base64, zlib
enc = base64.urlsafe_b64encode(zlib.compress(소스.encode("utf-8"), 9)).decode("ascii")
url = "https://plantuml.sumzip.com/plantuml/svg/" + enc      # 경로는 반드시 /plantuml/svg/
```

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' --max-time 20 "<렌더URL>"   # 200 image/svg+xml
```

- **HTTP 400 이면 문법 오류다**(Kroki가 컴파일에 실패한 것). 200 이어도 SVG 안에 `Syntax Error` 가 있으면 실패다.
- URL은 **4096자 이하**(실측 4053 통과 · 4121 → 414). 넘으면 프로세스를 더 잘게 나눈다.
- 소스를 고치면 **반드시 재인코딩**한다. 복호해서 코드블록과 대조한다:
  `zlib.decompress(base64.urlsafe_b64decode(enc + "==")).decode("utf-8") == 코드블록_원문`
- 삽입 형식: 코드블록 바로 아래 `**[「<제목>」 PlantUML 뷰어로 열기](<url>)** — 클릭 시 브라우저로 연결됩니다.`
- 렌더 서버에 닿지 않으면 `주의: 렌더 검증 미수행` 을 적는다. **검증했다고 쓰지 않는다.**

### [검증 — 저장 직전 자가점검]

- [ ] **모든 UC가 어느 프로세스로 갔는가** — 미사상 UC 0건인가
- [ ] 모든 IPO 행에 **UC·절 단위 근거**가 붙었는가
- [ ] 모든 게이트에 **조건 · 미통과 결과 · 해제 주체**가 각각 있는가 (해제 주체 없는 게이트 0건)
- [ ] 게이트가 UC의 예외흐름에서 도출되었는가 (원천 없는 게이트를 만들지 않았는가)
- [ ] 인계 계약 표에 **만료·무효 조건**이 있는가
- [ ] §1-4 **BPMN 대응표**가 실려 있는가
- [ ] 모든 다이어그램에 `start` 1개와 명시적 종료(`stop`·`kill`)가 있는가
- [ ] 차단 종료가 `kill` + 색으로 구분되는가
- [ ] 모든 렌더 링크가 **curl 200 · image/svg+xml** 이고 `Syntax Error` 가 없는가
- [ ] 링크를 복호한 소스가 **코드블록과 글자까지 같은가** · URL 4096자 이하인가
- [ ] 비기능 요구를 지어내지 않고 미해결 절에 남겼는가
- [ ] 이모지·긴 URL 노출이 없는가

### [금지]

- UC에 없는 단계·액터·외부시스템 생성
- 게이트를 "경고" 수준으로 약화 (차단이 아니면 게이트가 아니다)
- 한 도면에 전 프로세스를 우겨넣기 (읽을 수 없으면 도면이 아니다)
- 이모지 · 긴 URL 원문 노출
